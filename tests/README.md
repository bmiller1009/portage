# tests

Six layers, per `docs/architecture/spec.md` §52. Portability is a claim the project makes about itself, and these suites are how that claim gets proven rather than asserted.

| Suite | Purpose | Environment | How to run | CI | Live credentials |
|---|---|---|---|---|---|
| `unit/` | Fast, isolated tests — pure logic, providers against fakes/mocks, API routers against a fake DB session. Includes what would elsewhere be called "contract" tests (`test_execution_provider_contracts.py`, `test_storage_provider_contracts.py` — the same behavioral checks run against every provider), conformance tests, and security-adjacent tests (`test_auth.py`, `test_api_auth_enforcement.py`) — see the note below on why those live here rather than in their own top-level directories. | None | `pytest tests/unit -v` | Every PR (`.github/workflows/ci.yml`, `test` job — with the provider-contract/security/conformance subsets also run as their own labeled steps) | No |
| `integration/db/` | Real persistence-layer behavior against a real PostgreSQL — reconciler claim/poll logic, idempotency races, migrations. | PostgreSQL (a service container in CI; a throwaway local Docker Postgres for manual runs) | `alembic upgrade head && pytest tests/integration/db -v` | Every PR (`persistence-tests` job) | No |
| `integration/` (root) | `test_s3_provider_minio.py` and other live-Kubernetes/MinIO checks that need infrastructure only the project's remote dev box has. | Real kind cluster, Spark Operator, MinIO | Manually over SSH on that box, or via `.github/workflows/live-provider.yml` | Weekly/manual (`live-provider.yml`), not on every PR | Yes (SSH to the dev box) |
| `contract/` | Reserved for a dedicated provider-contract runner, if one becomes necessary beyond what `tests/unit/test_execution_provider_contracts.py`/`test_storage_provider_contracts.py` already cover. No files yet — not a gap, just not needed: the contract-test *content* already exists and already runs on every PR, just under `tests/unit/`. | — | — | — | — |
| `security/` | Secret-leakage / credential-logging tests (`test_secret_leakage.py`, as of v1.0.0's security review — see [`security/README.md`](security/README.md)). Auth/RBAC tests (missing auth, expired/wrong-audience/wrong-issuer tokens, insufficient role, escalation attempts) still live at `tests/unit/test_auth.py`/`test_api_auth_enforcement.py` — see the note below on why. | None | `pytest tests/security -v` (plus `tests/unit/test_auth.py tests/unit/test_api_auth_enforcement.py -v` for the auth/RBAC content) | Every PR (as the "Security tests" labeled step) | No |
| `e2e/` | Reserved for cross-provider portability fixtures beyond what `examples/claims_app` + `tests/unit/test_conformance.py`/`test_certification.py` + `plane conformance test`/`report` already prove live. No files yet. | — | — | — | — |
| `chaos/` | Live fault-injection against a real cluster with `charts/portage` installed — control-plane restart recovery, provider outage recovery, idempotent submission under real concurrency, HA dual-replica-kill. Spec §57's "mandatory v1.0 acceptance test." See [`chaos/README.md`](chaos/README.md). | Real kind cluster, Spark Operator, MinIO, `charts/portage` release | Manually over SSH on the dev box, or via `.github/workflows/live-provider.yml` | Weekly/manual, not on every PR | Yes (SSH to the dev box; Databricks OAuth M2M for the Databricks leg) |

**Why some "contract"/"security" test content lives under `tests/unit/` instead of `tests/contract/`/`tests/security/`**: those suites were scaffolded early (empty directories, own READMEs) before most of the actual test content existed. Provider-contract tests fit naturally as `tests/unit/` files (no live infrastructure needed, fast, deterministic) and stayed there — moving them now would be pure churn for no behavioral gain; `tests/contract/` stays a placeholder for a dedicated multi-provider contract *runner*, not reserved for content that already exists elsewhere. `tests/security/` is different: as of v1.0.0's security review, it holds genuinely new, cross-cutting content (`test_secret_leakage.py`) that doesn't belong to any one module's own test file — auth/RBAC tests remain under `tests/unit/` since they're one module's (`api/auth.py`) behavioral contract, the same category as everything else there.
