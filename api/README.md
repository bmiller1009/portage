# api

The FastAPI application: routers, request/response schemas, and the OpenAPI surface described in `docs/architecture/spec.md` §30. This is the only HTTP entry point into the control plane — the CLI, SDK, and UI are all clients of this API, not privileged callers.

Currently implemented: `GET /health`, `GET /ready` (`main.py`); CRUD for `/v1/execution-profiles`, `/v1/storage-profiles`, `/v1/environments`, `/v1/datasets`, `/v1/workloads`; `POST /v1/runs`/`GET /v1/runs/{id}`/`GET /v1/runs/{id}/events`/`DELETE /v1/runs/{id}`/`GET /v1/runs/{id}/logs`; and `POST /v1/validate` (`routers/`) — all backed by real PostgreSQL persistence (`control_plane/db.py`/`models.py`/`repositories.py`/`run_service.py`, `alembic/`). `POST /v1/runs` only ever writes `ACCEPTED` and returns; `DELETE /v1/runs/{id}` only ever records cancellation intent (`CANCELING`) unless the run was never submitted, in which case it finalizes immediately — `reconciler/` is what actually talks to the provider in both cases (submit, poll, cancel), verified live against the remote Kubernetes cluster. `GET /v1/runs/{id}/logs` and `POST /v1/validate` are the two exceptions: both read-only against the provider, so they're answered synchronously in the request handler rather than deferred to the reconciler. `POST /v1/validate` takes an inline workload definition (not a registered one) plus an environment name, resolves the provider, and runs the same capability-matching `validate()` call the reconciler makes before submission (spec §20-21) — so a passing `plane workload validate --environment` really does predict what submission would do. `plane` (the CLI) is a pure REST client of this API — no more direct provider access (`cli/main.py`).

Business logic belongs in `control_plane/`, not here — routers should stay thin and delegate.
