# reconciler

The async worker that owns the submit/poll/converge loop described in `docs/architecture/spec.md` §24: it validates a `RunRequest`, submits it to the appropriate `ExecutionProvider`, polls or watches provider status, and updates the canonical run state in PostgreSQL.

This separation is what makes control-plane failure non-fatal to running Spark jobs (§4.5, ADR 0007): once a workload is submitted, the execution provider owns it, and the reconciler just rediscovers and converges state on restart.

Implemented and live-verified — `service.py`'s `submit_new_runs()`/`poll_active_runs()`/`cancel_runs()` (called in sequence by `reconcile_once()`, run continuously by `main.py`) actually submitted a wordcount run to the real remote Kubernetes cluster via `POST /v1/runs`, drove it through `ACCEPTED → QUEUED → SUBMITTING → RUNNING → SUCCEEDED`, and the resulting output was verified correct in MinIO — the full database-backed control-plane path, not the Phase 0 CLI-direct one. `cancel_runs()` picks up `CANCELING` runs (recorded by `DELETE /v1/runs/{id}`), calls `provider.cancel()`, and finalizes to `CANCELED` — verified live against a real in-flight SparkApplication, which the reconciler actually deleted from the cluster. Per-run exceptions are caught and turned into a `FAILED` transition rather than crashing the loop (ADR 0007). Tested against real Postgres with a fake `ExecutionProvider` in `tests/integration/db/test_reconciler.py` (CI-run); the live Kubernetes submission and cancellation were checked by hand, same pattern as the rest of Phase 0/v0.1.

Restart-recovery under an actual control-plane outage (spec §57's mandatory v1.0 acceptance test) isn't exercised yet — this only proves the reconciler drives a run to completion, not that it survives being killed mid-run.

`submit_new_runs()` also resolves `workload.application.artifact` through the persisted `ArtifactBinding` table (spec §51) before building `ResolvedWorkload` — an `artifact://name/version` reference becomes a real, environment-specific URI, so providers only ever see something they can actually fetch. Live-verified: a JVM JAR workload referencing `artifact://spark-examples/1.0.0` reached `SUCCEEDED` on the real cluster, with the submitted `SparkApplication`'s `jars` field showing the *resolved* `s3a://` URI — proof Spark genuinely downloaded and ran the jar from S3, not a value that merely looked right in the database. A non-`artifact://` reference (e.g. a `local://` path baked into an image) passes through unchanged — the abstraction is opt-in.

`main.py` also serves `GET :9091/metrics` (port via `PORTAGE_RECONCILER_METRICS_PORT`) — `control_plane/metrics.py`'s OpenTelemetry-instrumented submission/queue/execution-duration histograms, provider-error counter, and reconciliation-lag gauge (spec §29), all recorded at the exact call sites in `service.py` that observe them. This lives on its own port because the reconciler is a separate process from the API (§4.5) with independent memory — see `control_plane/metrics.py`'s docstring for the full reasoning, including why run-outcome counts are split across both processes' `/metrics` rather than unified in one place. Live-verified: after a real run, `curl :9091/metrics` shows non-zero submission/queue/execution histograms with real timings (~4s/~5s/~55s for a live wordcount run) and a small `reconciliation_lag_seconds`.
