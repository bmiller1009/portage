# Portage 1.0.1 verification

Records exactly what was validated for the 1.0.1 patch release — not a marketing summary. Terminology (consistent with the compatibility matrix in the top-level README and `docs/verification/v1.0.0.md`):

- **SUPPORTED** — the code path exists and is exercised by tests.
- **AVAILABLE** — confirmed to exist/be compatible via a live infrastructure query, but no full workload was actually run under it.
- **TESTED** — actually run against real infrastructure at least once.
- **CERTIFIED** — passes the applicable automated contract/conformance suite (deliberately fake/mock-backed for most components, by design — see `tests/README.md`) **and** has separate, corresponding live-infrastructure evidence for that exact component or provider combination; passing the contract suite alone is not sufficient.
- **EXPERIMENTAL** — implemented and unit-tested against fakes only; no real infrastructure available to this project to test against.
- **NOT_RUN** — genuinely not exercised this pass; never inferred as passing.

**Git tag `v1.0.1` → commit `<final>`** (recorded at the bottom, once known — a commit cannot embed its own hash). Everything below happened on `main` after `v1.0.0` (tag → commit `0c03415`; see [`docs/verification/v1.0.0.md`](v1.0.0.md) for that release's own record, which this document does not repeat). 1.0.1 is a patch release: one real behavioral fix (the certification cross-product bug) plus documentation/wording/formatting corrections — no new features, no architecture changes.

## RC wording/redaction pass

A small, documentation-only pass ahead of what was originally going to remain part of `v1.0.0` but landed after the tag was already cut. Two real fixes:

1. **Byte-identical vs. semantic-equivalence wording.** Six documents (`README.md`, `docs/verification/v1.0.0.md`, `docs/releases/development-history.md`, `docs/providers/databricks.md`, `examples/README.md`, `conformance/README.md`) stated the hero run's "byte-identical output" as a bare fact with no nearby distinction from Portage's actual formal guarantee (semantic equivalence, ADR 0011). All six now state the guarantee first and byte-identical output as that run's additionally-observed result, not the contract itself.
2. **Infrastructure hostname redaction.** The real Databricks workspace hostname, published in `docs/providers/databricks.md` and (at the time) `docs/verification/v1.0.0.md`, was redacted — it added no verification value while every other piece of technical evidence (runtime versions, auth mechanism, Serverless/classic distinction, live results) was preserved. The real dev-box IP used as an example in `.github/workflows/live-provider.yml`'s secrets comment was genericized.

A manual credential-pattern sweep across the full repository (AWS access-key-ID shapes, Databricks/OAuth token shapes, private-key blocks, JWT shapes, generic `secret`/`password`/`api_key` assignments to non-placeholder values, signed-URL query-param shapes) found nothing.

## Certification cross-product fix

A real, self-documented bug, not a documentation-only issue: `control_plane/certification.py`'s `_status_for()` computed `PASS` as a cross-product of two independently-verified sets (`_LIVE_VERIFIED_EXECUTION_PROVIDERS × _LIVE_VERIFIED_STORAGE_PROTOCOLS`), so a combination could report `PASS` purely because each *side* had been live-verified somewhere, without that exact *pair* ever having been run together — the function's own comment already named `(databricks, vast-s3)` as the exact false positive. Confirmed real by the existing test suite, which asserted `("kubernetes", "vast-s3") → PASS` as correct — wrong, since no Kubernetes-execution + VAST-S3-storage workload was ever submitted and run.

**Fix**: replaced the two independent sets with a single explicit `_LIVE_VERIFIED_COMBINATIONS = {("kubernetes", "s3"), ("databricks", "s3")}` — the only two pairs with actual pair-level workload-execution evidence (real MinIO across every milestone; Databricks Serverless + Unity Catalog Volumes registered as `s3`, issue #62's Spark 4.2 run). `("kubernetes", "vast-s3")` and `("databricks", "vast-s3")` now correctly report `BLOCKED` — VAST-S3's own storage-provider code remains defensibly live-tested (it delegates entirely to the already-live-tested `S3StorageProvider`), but that's evidence about the storage component alone, not about either execution provider having actually been paired with it. Documented as a design invariant in `docs/architecture/spec.md` §78 ("capabilities compose, verification evidence does not") and in `README.md`'s "Certified combinations" table.

**Test changes**: fixed the wrong `("kubernetes", "vast-s3") → PASS` assertion to `BLOCKED`; added `("databricks", "vast-s3") → BLOCKED` as an explicit case; added `test_independently_verified_providers_do_not_imply_verified_pair`, a regression test that enumerates every pair drawn from independently-verified sides and asserts each one not itself in `_LIVE_VERIFIED_COMBINATIONS` reports `BLOCKED` — it would fail if the cross-product pattern were ever reintroduced. `tests/unit/test_certification.py`: 13 tests, up from 11 (+2 new).

**Scope boundary**: `STATUS_PASS`/`STATUS_FAIL`/`STATUS_BLOCKED` (the public `GET /v1/conformance/report` contract, consumed by the CLI and `ui/src/pages/Conformance.tsx`) are unchanged — only which pairs earn `PASS` changed. No provider submission/execution/storage-resolution behavior touched.

**Live verification**: `NOT_RUN` — no SSH access to the remote dev box or local `kind` cluster was configured/available in the session that made this fix, so `plane conformance report` could not be re-run live against real infrastructure to visually confirm the corrected report output. This is a narrower gap than it sounds: `_status_for()` is a pure function with no I/O, and the unit tests exercise it directly against the exact real production provider/protocol strings (`"kubernetes"`, `"databricks"`, `"s3"`, `"vast-s3"`, `"vast-nfs"`, `"adls"`) with full behavioral coverage — a live re-run would only reconfirm that the previously-registered environments still exist, not add coverage of the logic itself.

## This release's own cleanup

- **`tests/README.md`**: the `unit/`, `security/`, and `chaos/` table-row cells were restructured with `<br>`-separated points instead of one dense unbroken paragraph per cell — the table was already structurally valid Markdown (checked repeatedly, including a byte-level scan for Unicode line-separator characters), but the wall-of-text cells read as broken in a plain-text view. Now genuinely scannable, still one valid row per suite.
- **`CERTIFIED` wording**: tightened in both `README.md` and `docs/verification/v1.0.0.md` — the old "passes the full automated provider-contract suite against real infrastructure" read as "the contract suite itself runs against real infra," which is backwards (most contract suites are deliberately fake/mock-backed, by design, for CI speed and determinism — see `tests/README.md`). New wording requires both a passing contract/conformance suite **and** separate live-infrastructure evidence.
- **`docs/verification/v1.0.0.md`**: fixed a real, confirmed contradiction — a since-removed section stated "the `v1.0.0` tag (at `cb88ab2`)," which was wrong; `cb88ab2` was just the last commit of the RC wording pass, not the tag target. The tag's actual, permanent target is `0c03415` (confirmed via `git rev-parse v1.0.0` / `git log -1 v1.0.0`). That document is now frozen to represent exactly what was true at `0c03415` and points here for everything after.
