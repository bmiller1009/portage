# Portage 1.0.0 verification

Records exactly what was validated for the 1.0.0 GA / public-release-hardening pass — not a marketing summary. Terminology (consistent with the compatibility matrix in the top-level README):

- **SUPPORTED** — the code path exists and is exercised by tests.
- **AVAILABLE** — confirmed to exist/be compatible via a live infrastructure query, but no full workload was actually run under it.
- **TESTED** — actually run against real infrastructure at least once.
- **CERTIFIED** — passes the full automated provider-contract suite against real infrastructure.
- **EXPERIMENTAL** — implemented and unit-tested against fakes only; no real infrastructure available to this project to test against.
- **NOT_RUN** — genuinely not exercised this pass; never inferred as passing.

**Record for the v1.0.0 GA / public-release-hardening pass**: last content commit `324f63c`, 2026-08-19 — 10 issues of the [v1.0.0 — Public Release](https://github.com/bmiller1009/portage/milestone/10) milestone closed (#58 tracking issue + #59–#67; #58 was inadvertently omitted from an earlier count here). ## Databricks

**Provider: TESTED (Serverless compute).** Real Databricks workspace (hostname withheld from this public verification record — adds no verification value), OAuth M2M authentication, Serverless compute (this workspace forbids classic clusters administratively — the classic-cluster submission path is implemented and contract-tested, never live-run). Spark 4.0/4.1/4.2 <-> Databricks Runtime 17.3 LTS/18.2/19 mappings all confirmed **AVAILABLE** via a direct `WorkspaceClient().clusters.spark_versions()` call during this pass — see `providers/execution/databricks/compatibility.py`. That's a distinct, weaker claim than a full workload run: only DBR 18.2/Spark 4.1 (the original `claims_app` hero-demo run, v0.3-era) and DBR 19/Spark 4.2 (a version-bumped copy of `examples/claims-normalization.yaml`, run this pass) actually reached `SUCCEEDED` end to end, with output confirmed in the target Unity Catalog volume; DBR 17.3/Spark 4.0 has never had a full hero-workload run, only its compatibility mapping confirmed live. `plane conformance report` was also confirmed live to correctly report `databricks + s3 -> PASS` after fixing a real staleness bug in `control_plane/certification.py` (see Known findings below).

## Kubernetes -> Databricks portability

**PASS.** `examples/claims_app` — the same workload file, same artifact reference, same logical dataset names — reached `SUCCEEDED` on both providers with semantically equivalent output, Portage's formal portability guarantee (ADR 0011 — schema, row counts, null counts, partition coverage, deterministic hashes, never physical file identity). In this specific run the output also happened to be byte-identical (verified in the prior v1.0/GA milestone; not re-verified byte-for-byte in this pass, since this pass's Databricks change only added a new supported Spark version, it didn't touch the join/normalize logic itself) — an observed bonus, not something future runs are required to reproduce.

## Security

- OIDC (JWT/JWKS verification), 5-role RBAC, machine identity (OAuth2 M2M), secret references (`credential_reference`), and audit logging (`AuditEvent`) are all real, implemented in `api/auth.py`/`control_plane/credentials.py`/`control_plane/audit.py`. TESTED: missing auth, expired token, wrong audience, wrong issuer, insufficient role, and explicit role-escalation attempts.
- TLS: ingress-terminated (`charts/portage`'s `Ingress` template, cert-manager-compatible), live-verified.
- Secret leakage: TESTED — `tests/security/test_secret_leakage.py`, plus a real logging-hygiene finding fixed (`ApiException.__str__()`'s raw header/body leak into `RunEvent.message`).
- Audit completeness: a real gap found and fixed — `datasets`/`artifacts`/`webhooks` routers had zero audit calls on mutating endpoints. Confirmed live against a real Postgres + the real FastAPI app.
- Cross-project access, malicious artifact URI, path traversal, configuration/Spark-conf injection, and SSRF are genuinely **NOT_RUN** — not silently assumed covered.

## Known findings from this pass (fixed, not just documented)

- **`providers/execution/databricks/provider.py`**: Databricks Runtime 19 (GA 2026-07-23) added Spark 4.2 support; the code still asserted no DBR shipped it. Fixed with a live-confirmed compatibility-table update.
- **`control_plane/certification.py`**: `plane conformance report` had been under-reporting Databricks as `BLOCKED` since v0.3 despite real live verification — `_LIVE_VERIFIED_EXECUTION_PROVIDERS` only listed `"kubernetes"`. Fixed and confirmed live.
- **`providers/execution/kubernetes/provider.py`**: `ApiException.__str__()`'s raw response headers/body were flowing into `RunEvent.message`, a real (if narrow) information-disclosure surface. Fixed to use structured status/reason fields only.
- **`api/routers/datasets.py`/`artifacts.py`/`webhooks.py`**: zero audit-event coverage on mutating endpoints, unlike every other config-resource router. Fixed and confirmed live.
- **`charts/portage`**: enabling `reconciler.rbac.create` without also listing every namespace Spark workloads actually submit into (not just the release namespace) produces a real, silent 403 Forbidden — found live while redeploying for this pass's closing chaos-suite run. Documented prominently in `values.yaml`; no code change needed (the feature works correctly once configured right), but the gotcha was real and easy to hit.

## Known caveats (accepted, not fixed this release)

- VAST NFS-mode and ADLS remain translation-layer-only (EXPERIMENTAL) — no hardware/subscription access. This is the one accepted, documented gap against spec §71's exit criteria, unchanged from the prior v1.0/GA milestone.
- Cross-project access, malicious artifact URI, path traversal, configuration/Spark-conf injection, SSRF, malformed provider payload — genuinely untested security scenarios, tracked for future work, not silently assumed covered.
- Chaos-suite Databricks-API-interruption coverage does not exist — no fault-injectable surface for a hosted third-party API.
- `.github/workflows/live-provider.yml` (scheduled live-infrastructure CI) requires repository secrets not yet configured by the repo owner — its first real scheduled/manual run is itself part of what verifies it works; the workflow's YAML is `actionlint`-clean but its actual execution is `NOT_RUN`.
- Spark Declarative Pipelines: spec-layer/manifest translation built and unit-tested, but running one to completion needs a persistent Spark Connect server as its own deployed resource — not built (unchanged limitation from v0.6).
